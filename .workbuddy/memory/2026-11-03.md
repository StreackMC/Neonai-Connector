# 2026-11-03

## ai.js「Context 传递」改动评估（未提交、未改代码）

用户先要做拓展法测试，随后改为只评估方案：**deprecate `askAI` 的 `caller`，新增互斥的 `context`（NeonaicCommandContext），
并让工具通过闭包拿到 ctx**。评估结论：方案方向对，但当前未提交实现有 P0 缺陷，必须重做注入方式。

### 当前改动（工作区 `M src/message/ai.js`）的实测/推演结论
1. **P0：所有基础工具被静默清空**。`buildToolSet` 改为返回 `{tools, toolsContext}` 后，
   `callProvider` 仍用 `neonaicChore.joinObject(baseTools, overrideTools)` 合并；`joinObject` 是**浅合并**
   （`src/utils/chore.js:191`）。`buildToolSet([])` 返回的 `{tools:{}, toolsContext:{}}` 会把 base 的两个键整体覆盖。
   已用真实 `joinObject` 验证：`{"tools":{},"toolsContext":{}}`。⇒ 任何 AI 调用都不再带工具（含拓展注册的工具）。
2. **日志与判空失真**：`toolNames = Object.keys(tools)` 现在是 `['tools','toolsContext']`，恒为 2；
   `extraCount = Object.keys(overrideTools).length` 恒为 2（没有临时工具也说「含临时 2」）。
   `...(toolNames.length ? tools : {})` 因此永不省略 `tools`，废掉了之前「无工具就不发 tools 键」的修复。
3. **`contextSchema: z.object({neonaic: z.object()})` 会把 ctx 剥成 `{}`**。zod 4（4.4.3）默认 strip 未知键，
   已用真实 `NeonaicCommandContext` 验证：`同一实例? false`、原型 `Object`、`executor: undefined`。
   即便没有合并 bug，工具拿到的也不是 ctx。
4. **`userInput: z.string()` 遇多模态必炸**：`buildToolSet` 收到的是 `buildUserContent(...)` 的返回值，
   含媒体时是数组（`src/message/ai.js` 的 `buildUserContent`），校验直接失败，工具无法执行。
5. 小问题：`defineAITool` 的 JSDoc 多了 `@param {string} [definition.input]`，`definition.input` 并不存在；
   `execute` 返回类型写成 `string`，实际允许对象/Promise。

### 对方案的判断
- **`context` 取代 `caller`：赞成**。`caller` 只是执行者链，丢掉了 `privateExecutor`；当前 `askAI` 还硬编码
  `privateExecutor: true`，群聊也会自称私密，一旦工具依赖这个字段就是隐私谎报。
  `messageIn` 本来就有完整的 `resolveCommandWith`（第 127 行还 `new NeonaicCommandContext(...)` 给命令用），
  改传 `context` 是顺手且更正确。真实调用点只有 3 处：`messageIn:172`、`joyous/methods.js:366`、`ai.js:967`。
- **闭包注入：方向对，但表述要修正**。全局注册的拓展工具（`registerAITool`）定义是一次性的，
  自己闭包不到 per-call ctx；真正可落地的形态是 **`buildToolSet` 每次调用时包装 `execute`**：
  `execute: (input, options) => def.execute(input, { ...options, neonaic: ctx, userInput })`。
  这既覆盖全局工具也覆盖临时工具，彻底不需要 `contextSchema`/`toolsContext`。
- **互斥判断必须看原始入参**：`joinObject` 的默认值里有 `caller: []`，合并后 `caller` 永远存在，
  用 `conf.caller` 判「是否传了」永远为真。要用 `options` 原对象 + `!= null`。
- **caller → ctx 的转换**：`privateExecutor` 应默认 `false`（安全），不能沿用当前的 `true`；
  `internalCall` 必须强制 `false`（`checkPermissionFromContext` 对 internalCall 直接放行，工具拿它做鉴权会被绕过）；
  建议 `clone()`，避免工具改到调用方的 ctx，也避免调用方后续追加 executor 影响在途请求。
  另外 `ctx.this` 会把平台对象透给工具，是否清掉需要拍板。
- **typedef**：建议 `execute(input, options)`，`options` 扩展为
  `ToolExecutionOptions & { neonaic: NeonaicCommandContext, userInput: string }`；
  `userInput` 建议传 `renderTextOnly(message)`（恒字符串），不要传构建后的多模态数组。

### 拍板结果（已实施）
1. `caller` 垫片的 `privateExecutor` 固定 **false**。
2. `context` 接受 `NeonaicCommandContext` **或普通对象**，内部 `new NeonaicCommandContext(...)` 包一层。
3. **清空 `ctx.this`**（工具是全局语义，平台对象容易泄漏/指代不明）；同时强制 `internalCall=false`。

## 实施（阶段提交）

验证时又抓到**第二个 P0**：`...(toolNames.length ? tools : {})` 把工具表直接展开，
工具名（`probe-ctx`）成了请求体顶层参数——即使合并修好，SDK 也认不出工具。两处一起修。

### 阶段一 `6f6be73` fix(ai)：工具集扁平化 + 调用期注入
- `buildToolSet` 恢复「模型名 → 工具」扁平表；base 与 override **一次 build**（同名时后者优先），
  不再对 `{tools,toolsContext}` 套 `joinObject`（浅合并会整体覆盖）
- `execute` 在 buildToolSet 里包装，注入 `options.neonaic` 与 `options.userInput`
- 去掉 `contextSchema`/`toolsContext`（zod 会把类实例剥成 `{}`，多模态时 `z.string()` 还会失败）
- 修回 `{ tools }` 包装；日志里的工具数与「含临时」数恢复真实值
- `userInput` 由 `plainTextOf()` 取纯文本，恒为 string

### 阶段二 `23d47c1` feat(ai)：context 取代 caller
- `askAI` 新增 `options.context`，与 `caller` **互斥**（看原始入参，不能看 `joinObject` 后的默认值）
- `toCommandContext()`：克隆、强制 `internalCall=false`、清空 `this`；普通对象自动 new
- `caller` 垫片 `privateExecutor=false`，每个进程只提示一次弃用
- `speaker` / 封禁检查改读 `ctx.executor`（只传 context 时 speaker 不再静默失效）
- 迁移 3 处调用点：`messageIn`（复用 `resolveCommandWith`）、`joyous ai.request`（显式非私密）、
  `aiProfile test`；顺带修掉 `ctx.caller`（该访问器根本不存在）

### 验证（沙箱 + 桩 fetch，未污染真实配置）
- 阶段一：基础工具仍在（`probe-ctx`）、base+override 同时存在、ctx 是真实实例、`userInput` 是字符串
- 阶段二：caller 垫片 `private=false`；真实 ctx 的 `private=true` 保留、`internalCall` 被强制 false、
  `this` 被清空且**不修改调用方对象**；普通对象/空对象可用（空 executor 是 `[]` 而非 `$unknown`）；
