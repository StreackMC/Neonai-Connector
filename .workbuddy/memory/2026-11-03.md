## ai.js「Context 传递」改动评估（未提交、未改代码）

用户先要做拓展法测试，随后改为只评估方案：**deprecate `askAI` 的 `caller`，新增互斥的 `context`（NeonaicCommandContext），
并让工具通过闭包拿到 ctx**。评估结论：方案方向对，但当前未提交实现有 P0 缺陷，必须重做注入方式。

### 当前改动（工作区 `M src/message/ai.js`）的实测/推演结论
1. **P0：所有基础工具被静默清空**。`buildToolSet` 改为返回 `{tools, toolsContext}` 后，
   `callProvider` 仍用 `neonaicChore.joinObject(baseTools, overrideTools)` 合并；`joinObject` 是**浅合并**
   （`src/utils/chore.js:191`）。`buildToolSet([])` 返回的 `{tools:{}, toolsContext:{}}` 会把 base 的两个键整体覆盖。
   已用真实 `joinObject` 验证：`{"tools":{},"toolsContext":{}}`。⇒ 任何 AI 调用都不再带工具（含拓展注册的工具）。
2. **日志与判空失真**：`toolNames = Object.keys(tools)` 现在是 `['tools','toolsContext']`，恒为 2；
   `extraCount = Object.keys(overrideTools).length` 恒为 2（没有临时工具也说「含临时 2」）。
   `...(toolNames.length ? tools : {})` 因此永不省略 `tools`，废掉了之前「无工具就不发 tools 键」的修复。
3. **`contextSchema: z.object({neonaic: z.object()})` 会把 ctx 剥成 `{}`**。zod 4（4.4.3）默认 strip 未知键，
   已用真实 `NeonaicCommandContext` 验证：`同一实例? false`、原型 `Object`、`executor: undefined`。
   即便没有合并 bug，工具拿到的也不是 ctx。
4. **`userInput: z.string()` 遇多模态必炸**：`buildToolSet` 收到的是 `buildUserContent(...)` 的返回值，
   含媒体时是数组（`src/message/ai.js` 的 `buildUserContent`），校验直接失败，工具无法执行。
5. 小问题：`defineAITool` 的 JSDoc 多了 `@param {string} [definition.input]`，`definition.input` 并不存在；
   `execute` 返回类型写成 `string`，实际允许对象/Promise。

### 对方案的判断
- **`context` 取代 `caller`：赞成**。`caller` 只是执行者链，丢掉了 `privateExecutor`；当前 `askAI` 还硬编码
  `privateExecutor: true`，群聊也会自称私密，一旦工具依赖这个字段就是隐私谎报。
  `messageIn` 本来就有完整的 `resolveCommandWith`（第 127 行还 `new NeonaicCommandContext(...)` 给命令用），
  改传 `context` 是顺手且更正确。真实调用点只有 3 处：`messageIn:172`、`joyous/methods.js:366`、`ai.js:967`。
- **闭包注入：方向对，但表述要修正**。全局注册的拓展工具（`registerAITool`）定义是一次性的，
  自己闭包不到 per-call ctx；真正可落地的形态是 **`buildToolSet` 每次调用时包装 `execute`**：
  `execute: (input, options) => def.execute(input, { ...options, neonaic: ctx, userInput })`。
  这既覆盖全局工具也覆盖临时工具，彻底不需要 `contextSchema`/`toolsContext`。
- **互斥判断必须看原始入参**：`joinObject` 的默认值里有 `caller: []`，合并后 `caller` 永远存在，
  用 `conf.caller` 判「是否传了」永远为真。要用 `options` 原对象 + `!= null`。
- **caller → ctx 的转换**：`privateExecutor` 应默认 `false`（安全），不能沿用当前的 `true`；
  `internalCall` 必须强制 `false`（`checkPermissionFromContext` 对 internalCall 直接放行，工具拿它做鉴权会被绕过）；
  建议 `clone()`，避免工具改到调用方的 ctx，也避免调用方后续追加 executor 影响在途请求。
  另外 `ctx.this` 会把平台对象透给工具，是否清掉需要拍板。
- **typedef**：建议 `execute(input, options)`，`options` 扩展为
  `ToolExecutionOptions & { neonaic: NeonaicCommandContext, userInput: string }`；
  `userInput` 建议传 `renderTextOnly(message)`（恒字符串），不要传构建后的多模态数组。

### 拍板结果（已实施）
1. `caller` 垫片的 `privateExecutor` 固定 **false**。
2. `context` 接受 `NeonaicCommandContext` **或普通对象**，内部 `new NeonaicCommandContext(...)` 包一层。
3. **清空 `ctx.this`**（工具是全局语义，平台对象容易泄漏/指代不明）；同时强制 `internalCall=false`。

## aicode 拓展（QuickJS 代码执行）审计 —— 未改代码、未提交

`extensions/aicode` 是**未跟踪的新拓展**（`main.js`/`package.json`/`package-lock.json` 也是改动中）。

### 结论：当前状态完全不可用，有 7 个互相独立的阻断点
1. **语法错误 1**：`entry.js:17` `const { eval } = ...` —— ESM 严格模式禁止 `eval` 作绑定名。
2. **语法错误 2**：`entry.js:29` 在**非 async** 的 `onDisable` 里 `await`。
3. **语法错误 3**：`sandboxmgr.js:20` `export async function eval(...)` —— 同上，绑定名非法。
4. **fork 目标不存在**：`sandboxmgr.js:26` 找 `sandboxeval.js`，实际只有 `src/eval.js`。
5. **`this.pwd` 不存在**：`entry.js:18`；`pwd` 只在 `onEnable` 的**参数**里（`extLoader.js:120-125`），
   `NeonaicExtItem` 只有 export/manifest/name/id/fullname/enabled。且 `execute(input, ctx)` 的
   `ctx` 把 `onEnable` 的参数遮蔽了，即使改写成 `ctx.pwd` 也会拿错。
6. **子进程必自杀**：`main.js:16` 设 `process.env.NEONAIC`，fork 默认继承；`eval.js:2` 见到它就
   `exit(1)`（已实测子进程能读到 `Neonai!!`）。
7. **IPC 方向全错**：`channel.emit('code'/'result'/'error')` **不跨进程**。实测：父 `channel.emit('code')`
   子进程收不到，只有 `child.send()`→`process.on('message')` 才行。所以代码永远送不进去、结果也永远回不来。

另：`cwd` 目录从未创建，`fork` 会发 `error`（ENOENT），而 `sandboxmgr` **只监听 `exit` 不监听 `error`**
⇒ 未捕获异常**打崩整个内核**（已实测）。超时/校验失败路径还有 5 处 `throw NeonaicXxxError(...)`
漏 `new`，实际抛的是 `TypeError: Class constructor ... cannot be invoked without 'new'`。

### 功能正确性
- **`evalCode` 是 ESM 求值，只回 `export default`**：`1+1` → `{ok:true}`（无 data）；
  `export default 1+1` → `{ok:true,data:2}`。工具宣称“获取结果”对普通代码不成立。
- `runSandboxed` **不抛错**，失败返回 `{ok:false,error}`；`eval.js` 不检查 `ok`，把错误当结果回传。
- **未设 `executionTimeout`**（库支持，实测 300ms 生效，返回 `ExecutionTimeout`）。同步 wasm 会阻塞事件循环，
  `eval.js` 的 30s/60s 看门狗在死循环期间根本不会触发；父进程 10s SIGKILL 是唯一兜底。
- 未设 `memoryLimit`/`maxStackSize`；无并发上限、无代码长度上限（每次调用 fork 一个 Node+wasm 进程）。
- `console.log` 默认转发到宿主 console（实测沙箱里的 `hi` 直接打到了宿主），可伪造/污染日志。

### 安全边界（实测）
- **合格**：`import('node:fs')` → “File access is disabled”；`node:child_process` → “module not implemented”；
  `fetch` 存在但抛 “disabled”；沙箱的 `process` 只是 `{env, cwd}` 垫片，`process.env.NEONAIC` 不可见。
- **过宽**：`execArgv: --allow-fs-read=<ROOT>` 把整个项目（含 `secret.json`）的读权限给了子进程；
  QuickJS 层挡住了，但属该收窄的纵深防御（文件入口下 `--permission` 实测可正常启动）。
- **无授权**：工具没有任何权限闸；任何能让 AI 调工具的用户（群聊成员/提示注入）都能执行代码。
  `ctx` 传进去了却只用来拼 cwd。

### 生命周期
- 内核没有 `unregisterAITool`；`onDisable` 只 abort forks，**停用后工具仍可调用**，且会重新 spawn。
- 超时 `setTimeout` 未 clear/unref；`cleanForks` 判 `fork.killed`（不代表已退出）且无人调用。

### 建议的最小修复顺序
改语法（`runInSandbox` 绑定、`onDisable` async）→ 用 `ctx.pwd` 且重命名参数 → fork 指 `src/eval.js`、
`mkdirSync(cwd,{recursive:true})`、补 `fork.on('error')` → IPC 改 `send`/`on('message')`（结果 `{ok,data,error}`，
`send` 回调后再 exit）→ 子进程 env 去掉 `NEONAIC` → 加 `executionTimeout`/`memoryLimit`、检查 `r.ok`、
返回 `data` → 加权限闸 + 并发/长度限制 + 自定义 `console` → 内核补注销 API。

## aicode：削峰缓冲调度 + 安全边界核查（下午）

### 调度：待机阶梯
- `maxChildren` 默认 2 → **10**（吸收突发）；`idleMinutes` 拆成 **`idleMaxMinutes`（最大待机时长）** + **`idleDecay`（递减系数）**，旧键仍兼容并记一条 issue。
- 预算用等差数列：`step = idleMaxMs * decay / 待机数`、`budget(i) = idleMaxMs - (k-1-i)*step`（i=0 最久没用）⇒ 进程越多杀得越快，最后一位恰好活满 `idleMaxMinutes`；`decay=0` 退化为同时到期；5s 下限防抖。扫描器**全池一个**（500–2000ms），到点直接 SIGKILL（待机进程无未完成工作，容量立刻释放）。
- 实测 k=10/decay=1 → `[5,5,5,5,5,5,6,7,8,9]`（单位秒，idleMax=9s）；k=2 → `[5,9]` 且按 5s/9s 分两批死亡。

### 修的三个真 bug
1. **交付即占用**：`acquire()` 返回前就 `busy=true`。原来「acquire 挑选、runOnWorker 置忙」会让两个并发任务挑中同一进程、后者覆盖 `worker.task`，前者永久悬挂（硬超时又 `id 不匹配就 return`）。实测 4 并发 → 2 ok + 2 busy（修前 3 个永久 hang）。
2. **fork 的 IPC 会把内核打死**：子进程往 fd 3 写 `{bad-frame}\n` ⇒ 宿主 `parseChannelMessages` 抛未捕获 SyntaxError，整个内核退出。改成 `spawn` + 两根私用管道（子读 fd3/写 fd4）+ 自研分帧（`\n` 分隔、半包/粘包、单帧 ≤1MB、非 JSON/非对象/超长即协议异常 → SIGKILL 子进程）。结果帧还要求 `id` 严格相等（原来「id 存在才校验」，省略 id 就能顶掉当前任务）。
3. **guest 只能回字符串**：库的 `handleToNative` 处理任何非原始值都漏句柄 → runtime 释放时 `JS_FreeRuntime` 断言 abort（修前 `return {a:1}` 直接打崩子进程）。现在 guest 内 `JSON.stringify` 成 `aicode:<status>\n<payload>`，宿主 `JSON.parse` + `sanitize.js`（深度/节点/数组/键/单串上限，丢 `__proto__`/`constructor`/`prototype`，超 512K 换 `{truncated,size,preview}`）。

### 权限模型实测（Node 22.22.2，`--permission --allow-fs-read=ROOT`）
拒绝：写盘/删盘、读 ROOT 之外、`child_process`、`process.binding`。
**不拦**：读 ROOT 之内（`secret.json` 直接读到）、网络（dns/tcp 全通）、继承环境变量、`process.kill(ppid)`（实测把父进程杀掉）。
⇒ 真被攻陷时拿不到写盘与起子进程，但读得到密钥、连得上内网、能杀内核；这三条只能外部兜（低权限用户/网络策略/密钥移出项目根）。

### 验证
- 帧编解码单测 9 项全绿（往返/粘包/逐字节半包/坏 JSON/非对象/数组/超长/违规后失效/空行）
- 端到端 12 例：对象/数组/类实例（修前全 abort）、BigInt/循环引用 → `UnserializableResult`、`__proto__` 被剥离、深嵌套 `[depth truncated]`、console 收集
