## joyous 拓展架构重构（HTTP/UDS 双通道 + 通信层解耦）

### 目标与结论
把原本「一个 entry.js 什么都干」的 joyous 拓展重构为分层架构，新增跨平台 UDS 通道，
并补齐原先完全缺失的「接收 JoyousPlugin 执行命令请求」链路。78 项沙箱自检 + 12 项加载器集成全部通过，
并对**本机真实运行的 JoyousPlugin（localhost:8080/japi/status）**做过联调，渲染结果与重构前日志逐字一致。

### 分层结果（`extensions/joyous/`）
- `src/entry.js` 组合根：读配置 → 装配通道 → 注册命令/AI 工具（声明式，模块顶层）→ 优雅关闭；`onEnable/onDisable` 幂等
- `src/config.js` 配置读取与归一化（`joyousConfig`），UDS 端点解析
- `src/status.js` 状态业务：只依赖注入的 `query(address)`，不认识 HTTP/UDS
- `src/protocol/` 通信层（用户指定平铺于此）
  - `constants.js` 协议唯一事实来源；`codec.js` JSON+`\n` 增量分帧
  - `session.js` 传输无关会话：握手状态机 + id 关联 + 心跳（不碰具体传输）
  - `http.js` 出=StatusAPI 客户端，入=命令服务端（`node:http`）
  - `uds.js` 跨平台主动连接 + 指数退避重连（复用 session）
  - `dispatch.js` **唯一接缝**：认识命令系统但不认识传输
- `PROTOCOL.md` 协议文档；`config.json` 拓展自带配置

### 关键设计决策（用户确认过的 4 项）
1. 通信模块落在 `${EXT_ROOT}/src/protocol` 内平铺（该目录下导入内核要用 **4 层** `../../../../src/...`）
2. UDS 端点**配置项驱动**：平台差异压缩到一个纯函数 `resolveUdsEndpoint(path, pipe, platform)`，其余代码全共用
3. 握手与帧格式由我设计并出文档（`PROTOCOL.md`）
4. 命令落地用 `$console` 同级的 **`$joyous` 虚拟身份**，白名单由既有权限系统实现

### `$joyous` 三层白名单（复用既有权限系统，未新增机制）
1. 总闸 `joyous.bridge.execute`（默认不授予 ⇒ 开箱即全关）
2. 命令自身声明的 `permissions`（原生 AND/OR/`!` 语义）
3. **空权限命令的补漏**：命令系统里 `permissions: []` 等价于「任何人可执行」，对不受信任的外部身份是漏洞，
   故要求额外持有 `joyous.command.<ns>:<name>`

### 内核改动（**只应有一处**）
- `NeonaicNewableError.js` 加 `NeonaicProtocolError`（带可赋值 `code` 字段）—— **通用错误词汇**，
  内核不认识任何拓展 → 不涉及耦合，保留在内核。
- ~~`commandInterface.js` 加 `COMMAND_ENUMS.FROM_JOYOUS`~~ **已撤销**，见下。

### 用户指出的设计问题：`$joyous` 不该写进内核枚举（我原设计错了）
「拓展与本体解耦」的判断标准：**会不会留下「本体只在某拓展存在时才有意义」的东西**。
- `FROM_JOYOUS` 写进 `src/command/commandInterface.js` → 本体凭空多出一份死常量，**违反解耦** →
  已移到 `extensions/joyous/src/protocol/dispatch.js` 的 `BRIDGE_EXECUTOR = '$joyous'`，且不再 import 内核枚举。
- `NeonaicProtocolError` → 通用概念，内核不提任何拓展名 → **不违反**，保留。
- 正确的心智模型：内核的 `$` 前缀只是**合成执行者的保留命名空间**（自身只占 `$console` / `$unknown`），
  拓展可在其中自取名字；权限系统按**执行者字符串**存授权，**根本不需要枚举登记** —— 原来那个枚举纯属多余。
- 已在内核 `COMMAND_ENUMS` 的 JSDoc 写明这条约定（**不点名任何拓展**），并加了两道自检守卫：
  ① `COMMAND_ENUMS.FROM_JOYOUS === undefined`；② **`src/` 全目录不得出现 `joyous` 字样**。
- 顺手修了同一处 JSDoc 的悬空引用：`{@link CommandContext.internalCall}` → `{@link import('./commandServer.js').NeonaicCommandContext}.internalCall`。

### 过程中发现并修掉的真缺陷
1. **握手首帧可能早于 `beginHandshake()` 到达** → 帧被静默丢弃、双方互等到超时。修：`#onHandshakeFrame` 见 IDLE 时补启动握手。
2. **超限请求体 `req.destroy()` 会让 413 响应发不出去**（客户端只看到连接重置）。修：改为 `req.resume()` 只排空。
3. **`JSON.parse('[1,2]')` 是合法对象但不是合法状态体** → 客户端要显式拒绝数组。
4. **`normalizeRequest` 抛的 `NeonaicIllegalArgumentError` 没有 `.code`** → 会被上层归为 `internal_error`。修：包一层转 `invalid_argument`。
5. **内核 `executeCommandSilent` 的 try/catch 只拦同步异常**，async 命令处理器抛出的异常以 Promise 拒绝逸出，
   不会被包成 `NeonaicCommandError`（`executeCommand` 同样漏掉，会产生未处理拒绝）。
   本次在 `dispatch.classify` 里兜住归为 `command_failed`；**内核侧建议后续单独修**。

## qqbot：按上下文选择 AI Profile（急件）

### 结论：这是零内核改动的事
`neonaicAI.askAI(msg, { AIlist })` **本来就是一个「允许用哪些 AI Profile」的参数**，而且内核已内置两层
可用性处理：`available === false` 直接跳过；列表内逐个 try、失败自动换下一个（`ai.js:379-387`）。
所以「按上下文选可用的 Profile」= 在调用点把 `AIlist` 算出来即可。

调用链：`QQ 事件 → msgHandler 两个入口 → resolveReply(msg,{AI,AIlist}) → askAI → callProvider`。
qqbot 原先在 `msgHandler.js` 传的是平台 Profile 的静态 `profile_config.allowedAI`。

### 关键不变量（反直觉，必须记住）
- **`AIlist` 只过滤、不决定顺序**：`ai.js:355` 是 `getList('oai').filter(...)`，filter 保持源顺序，
  所以**实际尝试顺序恒等于 `secret.json.oai` 的声明顺序**。
  ⇒ `use:["dev"]` 能表达「只用 dev」；**`use:["dev","deepseek"]` 不能表达「dev 优先、失败退到 deepseek」**。
- 因此「按上下文选单一 Profile」完全够用、0 改动；需要**上下文内的非全局优先级**时才需改 `ai.js` 那 3 行。
- **`PlatformManager` 构造 profile 时是 `{ ...raw, _debug }`（`platformManager.js:63`）**，自定义键原样透传
  ⇒ 平台级配置可以就近写进 `secret.json` 的 `platforms[]`，**不需要内核「支持」它**。
- 当前 `oai` 顺序：`deepseek(可用) → dev(禁用) → 3ban(禁用) → zai-glm-4.5-air(禁用) → zai-glm-4.7-flash(可用)`。
  ⇒ **路由到 `dev`/`3ban` 目前等于没路由**（会被静默跳过），要先 `/neonaic:ai profile enable <name>`。
- `resolveReply` 里 `AI` 开关（平台 `useAI`）决定「用不用 AI」；路由只决定「用谁」，两者正交。
