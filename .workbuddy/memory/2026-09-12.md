  - `load` / `unload`（+ `loadAll` / `unloadAll`）只动运行期，不碰配置；`unload` 沿用用户标注的 `@deprecated`（内存泄漏风险）
  - `enable` / `disable`（+ `enableAll` / `disableAll`）只动 `config/saves/ext.json` 里的开关，**默认不影响正在运行的拓展** —— 严格对齐 `NeonaicExtItem.enabled` 注释「不会影响插件的现行状态」，也避免把 deprecated 的卸载路径变成默认行为

## 修正：返回结构改为严格遵循用户写的 @typedef

- 用户反馈（原话「写的什么玩意」）：我把自己造的 `running` / `enabled` 字段当成契约，还删掉了他们写的两个 `@typedef`，JSDoc 里 `{@link NeonaicExtOperateStatusPayload}` 一度是悬空引用。
- 他们随后在文件里补写了 typedef（`325f660` 提交时已在），要点：
  - payload = `{ operation, status, error, id }`；`operation` ∈ `load|unload|enabled|disabled`（注意 enable/disable 的 operation **是过去分词形式**）；`status` ∈ `notfound|successfully|failed|disabled`，且 `disabled` 只能在 `operation='load'` 时出现
  - 批量 = `{ operation, succeed, notfound, disabled, failed }`——**没有 `affected`**（他们从早期草稿里去掉了），并且多了 `disabled` 分桶
- 据此重写：`resultOf()` 只产出那四个字段；`loadExt` 对「找到但被禁用」不再走异常包装，而是直接返回 `status:'disabled'`；`operateListed` 改为四桶且去掉 `affected`；`enable/disable` 的 operation 用 `enabled/disabled`。
- 唯一一处动了他们 typedef 的地方：批量 typedef 的 `operation` 联合从 `'load'|'unload'` 扩到 `'load'|'unload'|'enabled'|'disabled'`（否则 `enableAll`/`disableAll` 无合法取值）——已在回复中单独点出。
- 运行状态不再塞进 payload：`renderStatus` / 命令按 id 回查 `EXT_MAP` 取得（`list()` 摘要仍带 `running`/`enabled`，那是另一套 API）。
- 验证：`/tmp/extmgr-test.mjs` 59 项全通过，新增两条针对新契约的断言（payload 键集合恰为 `['error','id','operation','status']`；批量 load 时被禁用的拓展落进 `disabled` 桶）。`config/saves/ext.json` 仍按字节还原。
