## `oai[].tools` 支持广义通配（修正注释与实现不符）

- 问题：`config/secret.json` 注释写「支持模糊匹配」，但 `matchToolPattern` 实际只做两种：带 `:` 的 fqn **完全精确**、不带 `:` 的按 name 跨命名空间**完全相等**。所以 `"ns:*"` / `"!ns:*"` 静默匹配 0 个（还进了 unmatched 提示）。
- 改法（`src/message/ai.js`）：新增 `globToRegExpSource(glob, starSrc)`（只把 `*` 当元字符，其余全转义；按 `split('*')` 分段转义再拼），`matchToolPattern` 按**第一个 `:`** 切成 `nsGlob` / `nameGlob` 两段分别转正则：命名空间段的 `*` → `[^:]*`（不跨 `:`），工具名段的 `*` → `.*`。省略命名空间时 `nsGlob='*'`，保持「不带前缀即跨命名空间」旧语义。
  - 结果语法：`"*"` / `"ns:*"` / `"*:name"`（≡ `"name"`）/ `"n*:a*"` / `"!ns:*"`；`"ns:"`、`"ns:a"` 仍不隐式前缀匹配。
  - 注册时 ns/name 都被规整为 `[a-zA-Z0-9_]`，段内无 `:`，所以按第一个 `:` 切分无歧义 —— 这也是这段实现的前提。
- 顺带：`ai tool test <ref>` 现在可能一次命中多个（`findTool` 复用同一匹配），改为命中多个时列出候选并报错，而不是静默执行第一个。
- 验证：`/tmp` 沙箱（rsync `src` + 软链 `node_modules`）里注册 3 个命名空间 / 5 个工具，19 条断言全通过；`node --check` 通过。
- 文档：`config/secret.json` 的 `tools` 注释按新语法重写，`resolvePatternList` / `resolveToolList` / `findTool` 的 JSDoc 同步。

## 新增 `oai[].providerTools`（Provider Held Tools）

- 语义：启用**由 Provider 服务端执行**的内置工具（`isProviderExecuted: true`），不需要本地 `execute`。与 `tools`（本地注册工具）**相互独立**，`tools: []` 不会挡住 `providerTools`。
- 白名单刻意排除 `applyPatch` / `computer` / `shell` / `localShell` / `customTool` / `toolSearch` / `programmaticToolCalling`：前几个要应用侧执行并回传结果（放进去只会在模型调用那一刻报「没有 execute」），后两个要额外 SDK 接线。白名单 = `codeInterpreter` / `fileSearch` / `imageGeneration` / `mcp` / `webSearch` / `webSearchPreview`。
- 配置写法：对象 `{ "webSearch": true | 选项对象 | [选项对象…] }`，或数组简写 `["webSearch"]`；`false`/`null` 显式关闭；数组值构造多实例（多 MCP server → `mcp`、`mcp_2`）。键名归一化：转小写并去掉 `_ - 空格`，所以 `web_search` ≡ `webSearch`。
- 实现要点：
  - ⚠️ **"用默认参数" 也必须传 `{}` 而不是 `undefined`**：`ProviderExecutedToolFactory` 会解构 options（`webSearchPreview()` 直接抛 `Cannot destructure property 'onInputStart'`）。`webSearch`/`codeInterpreter`/`imageGeneration` 这类 `(args?)` 才容忍 undefined。
  - 模型可见名取 `tool.id` 最后一段（`openai.web_search` → `web_search`）；SDK 的 `prepareTools` 用**记录键**当 provider 工具的 `name`，`id` 才决定序列化。
  - ⚠️ **只有 Responses API 生效**：`prepareChatTools` 的 `switch (tool.type)` 只认 `function`，provider 类型只 push 一条 `unsupported` warning 就**静默丢弃**（没有任何报错）。所以 `providerTools` 非空而 `responseAPI: false` 时直接抛 `NeonaicIllegalArgumentError`。
  - `askAI` 的 per-profile 循环会把该错误包成 `NeonaicNetworkError("所有 AI Profile 请求失败: …")`，错误文本里仍带原始说明（既有语义，未改）。
- 验证：`/tmp` 沙箱 + 打桩 `globalThis.fetch`，24 条断言全通过。Responses 请求体实测：`[{type:'web_search',search_context_size:'medium'},{type:'code_interpreter',container:{type:'auto'}},{type:'mcp',server_label:'srv-a',require_approval:'never',server_url:…},…]`；混表时 function 工具在 Responses 下是**扁平** `{type:'function',name}`（Chat 下才是 `{type:'function',function:{name}}`）。

## 新增 `oai[].extraTools`（第三方平台的自定义工具类型）

- 起因：`providerTools` 那条通道只认 OpenAI 官方内置工具。`@ai-sdk/openai` **没有任何透传自定义工具类型的能力** —— Chat 的 `prepareChatTools` 只认 `function`（其余 push `unsupported` warning），Responses 的 `prepareResponsesTools` 里 `switch (tool.id)` **连 default 都没有**，未知 id 无声消失（连 warning 都收不到）。所以 deepseek 这类要求 `{"type":"deepseek_web_search"}` 的平台无法走 SDK。
- 方案：`extraTools`（键 = 条目 `type`，值 = 其余字段，`true`/`{}` 表示只有 type，数组 → 多条，`false`/`null` 跳过）+ `createExtraToolsFetch()` 作为 `createOpenAI({ fetch })` 中间件，在请求体序列化**之后**把条目追加进 `tools` 数组。只在配了注入项时才装中间件，其余 Profile 仍走原生 fetch。
  - 中间件要点：body 非字符串（FormData 等）或非合法 JSON → **原样透传**（注入失败不该把请求搞坏）；按 `type` 幂等，SDK 已写过的不重复加；⚠️ 必须**在调用时**才取 `globalThis.fetch`，提前捕获会让自检脚本的桩打空。
  - 键里写了不同的 `type` → 直接报错（自相矛盾，不静默覆盖）。
  - ⚠️ 注入的工具 AI SDK 不认识：平台若返回 tool_call 要求客户端执行 → `NoSuchToolError`。只适用于服务端执行、结果直接写进回复的工具。
- 顺带：`providerTools` 的未知键报错里加了一句「第三方平台自定义工具请写进 extraTools」；`callProvider` 里的局部变量 `extraTools` 改名 `overrideTools`（避免与配置同名混淆），日志加 `+ 注入 N`。
- 验证：Chat 端点实测 body.tools = `[{type:'function',function:{name:'neonaic-echo',…}},{type:'deepseek_web_search'},{mode:'fast',top_k:3,type:'deepseek_rerank'}]`，16 条断言全通过。
